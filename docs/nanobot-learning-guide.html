一、项目总览

是什么

nanobot 是一个超轻量级个人 AI 助手框架，灵感来自 OpenClaw，用约 99% 更少的代码实现了完整的 Agent 能力。它把「LLM 循环 + 工具调用 + 多渠道接入 + 持久记忆 + 定时任务」收敛成一套清晰、可读、易扩展的代码，特别适合学习 Agent 原理与二次开发。

网关服务nanobot gateway同时接入 Telegram/Slack/微信等多渠道

二、整体架构

分层架构图

nanobot 的核心思想是用消息总线（MessageBus）把「渠道层」与「Agent 核心」解耦，再用 AgentRunner 把纯粹的 LLM 循环从产品逻辑里抽离出来。

┌───────────────────────────────────────────────────────────────┐ │ 渠道层 (channels/) │ │ Telegram · Slack · Discord · 微信 · 飞书 · 钉钉 · QQ · Matrix │ │ 每个继承 BaseChannel：收消息→鉴权→InboundMessage │ └───────────────────────────┬───────────────────────────────────┘ │ publish_inbound / consume_outbound ▼ ┌───────────────────────────┐ │ MessageBus (bus/queue) │ 两条 asyncio.Queue │ inbound / outbound │ 彻底解耦收发 └─────────────┬─────────────┘ ▼ ┌─────────────────────────────────────────────┐ │ AgentLoop (agent/loop.py) │ │ · 按 session 串行、跨 session 并发 │ │ · /命令 优先分发 · checkpoint 中断恢复 │ │ · 注册默认工具 + 连接 MCP │ └───┬───────────────┬───────────────┬─────────┘ │ │ │ ▼ ▼ ▼ ContextBuilder SessionManager MemoryConsolidator (拼 prompt+history) (JSONL+缓存) (token 触发压缩) │ ▼ ┌──────────────────────────────────────┐ │ AgentRunner (agent/runner.py) │ ← 纯执行引擎 │ for iter in range(max_iterations): │ │ snip history → 调 LLM → 工具循环 │ │ 贯穿 AgentHook 生命周期 │ └───┬──────────────────────┬───────────┘ │ 调用 │ 执行 ▼ ▼ LLMProvider ToolRegistry (base + 各后端) (filesystem/shell/web/cron/mcp/spawn/message)
💡
设计要点：「AgentRunner 不知道渠道、不知道 session」——它只接收一个 AgentRunSpec（消息+工具+模型+回调），返回 AgentRunResult。这让同一套循环逻辑能被 CLI、网关、API、子代理、心跳复用。

消息数据流

用户消息 ↓ 渠道 SDK 回调 BaseChannel._handle_message() # 鉴权 is_allowed(sender_id) ↓ InboundMessage(channel, sender_id, chat_id, content, media, metadata, session_key_override) # 线程级会话可覆盖 key ↓ bus.publish_inbound() AgentLoop.run() 消费 → _dispatch() # 取 per-session 锁 + 全局并发信号量 ↓ _process_message(): 1. sessions.get_or_create(key) # 载入/新建会话（带内存缓存） 2. restore_runtime_checkpoint() # 崩溃/重启后恢复未完成回合 3. memory_consolidator.maybe_consolidate() # token 超预算→压缩旧消息 4. 处理 /命令（commands.dispatch） 5. context.build_messages(history, ...) # system + 历史 + 当前 6. AgentRunner.run(spec): 循环：snip_history → provider.chat_*_with_retry → 工具执行 → 回填 7. _save_turn() 写回 session.messages 8. 后台再触发一次 maybe_consolidate ↓ OutboundMessage → bus → ChannelManager._dispatch_outbound() ↓ 流式 delta 合并 + 失败重试(1s/2s/4s) Channel.send() → 用户

三、核心模块逐一解析

3.1 AgentLoop —— 消息编排引擎

nanobot/agent/loop.py

AgentLoop 是整个系统的「大脑外壳」，负责把一条消息从进入到回复的全流程串起来，但把真正的 LLM 循环委托给 AgentRunner。

关键职责

职责说明
消息分发run() 从 bus 持续消费；_dispatch() 按 session 加锁串行，跨 session 用全局信号量 NANOBOT_MAX_CONCURRENT_REQUESTS 并发
命令优先/stop /restart /status /reset 是 priority 命令，不进 LLM、不抢 session 锁，崩溃时也能用
上下文构建调用 ContextBuilder 生成 system prompt + history
工具注册_register_default_tools() 注册文件/Shell/Web/Message/Spawn/Cron；延迟连接 MCP
记忆压缩处理前同步、处理后异步各触发一次 maybe_consolidate_by_tokens
断点续传checkpoint 把「assistant 消息 + 已完成工具结果 + 待执行工具」存入 session.metadata，重启后恢复

内部 Hook：_LoopHook

AgentLoop 把产品层关切（流式、进度、去 <think> 标签、工具上下文）封装进 _LoopHook，再与用户自定义 hook 组成 _LoopHookChain 一起传给 runner：

# _LoopHook 关键回调
wants_streaming()      → 是否启用流式
on_stream(delta)       → 累积 delta、剥离 think 标签后增量发布到渠道
before_execute_tools() → 记录工具调用、设置工具上下文(channel/chat_id/message_id)
after_iteration()      → 记录 token usage
finalize_content()     → 去掉 think 标签产出最终文本

3.2 AgentRunner —— 纯 LLM 循环引擎

nanobot/agent/runner.py

这是「Agent」的心脏：一个标准的「调用 LLM → 若有工具调用则执行 → 回填结果 → 再调 LLM」循环，直到产出最终文本或触达停止条件。

输入 / 输出契约

@dataclass(slots=True)
class AgentRunSpec:
    initial_messages: list[dict]   # system + history + 当前消息
    tools: ToolRegistry
    model: str
    max_iterations: int            # 默认 200
    max_tool_result_chars: int     # 工具结果截断
    concurrent_tools: bool = False # 同批 read-only 工具并发
    context_window_tokens: int | None = None
    provider_retry_mode: str = "standard"  # 或 "persistent"
    progress_callback / checkpoint_callback / hook ...

@dataclass(slots=True)
class AgentRunResult:
    final_content: str | None
    messages: list[dict]
    tools_used: list[str]
    usage: dict[str, int]
    stop_reason: str   # completed / error / max_iterations / tool_error / empty_final_response

主循环逻辑

for iteration in range(max_iterations): 1. _apply_tool_result_budget() # 截断过长工具结果 2. _snip_history() # 按 context_window 倒序保留最新消息， # 并确保以完整 user 回合开头 3. before_iteration(hook) 4. response = provider.chat_stream_with_retry(...) # 流式优先 5. if response.has_tool_calls: · on_stream_end(resuming=True) · 构造 assistant_message(content + tool_calls) · checkpoint(phase="awaiting_tools") · _execute_tools() # 并发/串行 · 回填每个 tool 结果消息 · checkpoint(phase="tools_completed") → continue else: # 最终回复 · clean = finalize_content(response.content) · 空响应？→ _request_finalization_retry() 强制回话 · 三种收尾：error / empty_final_response / completed else: # 跑满迭代 stop_reason = "max_iterations"
🔍
工具并发模型：_partition_tool_batches() 依据每个工具的 concurrency_safe（= read_only and not exclusive）把调用分批：read-only 的批内用 asyncio.gather 并发，有副作用的串行执行。

3.3 Hook 体系 —— 可组合的生命周期

nanobot/agent/hook.py

Hook 是 nanobot 实现「不改核心代码即可扩展」的关键。所有自定义行为都通过实现 AgentHook 接口注入。

Hook 方法时机典型用途
wants_streaming()初始化声明需要流式 delta
before_iteration(ctx)每轮开始改写消息、埋点
on_stream(ctx, delta)流式每个 chunk实时转发到渠道
on_stream_end(ctx, resuming)流结束resuming=True→工具将执行；False→最终回复
before_execute_tools(ctx)工具执行前记录、设置上下文
after_iteration(ctx)每轮结束统计 usage、checkpoint
finalize_content(ctx, content)产出最终文本同步管道式过滤（如去 think）

CompositeHook 把多个 hook 扇出执行：异步方法异常隔离（单个 hook 报错不影响其他），而 finalize_content 是串联管道（不隔离，让 bug 浮现）。

3.4 ContextBuilder —— prompt 拼装

nanobot/agent/context.py

负责把「身份 + bootstrap 文件 + 记忆 + 技能 + 历史 + 当前消息」拼成最终发给 LLM 的 messages 数组。

system prompt 组成（用 --- 分隔）

build_system_prompt(): 1. _get_identity() # 运行时(OS/Python)、workspace 路径、平台策略、使用准则 2. bootstrap 文件 # AGENTS.md / SOUL.md / USER.md / TOOLS.md（存在才加） 3. memory.get_memory_context() # MEMORY.md 长期记忆 4. 常驻技能(always=true) 5. 技能摘要(XML，渐进式加载，LLM 用 read_file 读全文)
⚠️
记忆污染要点：MEMORY.md 的内容每次都会拼进 system prompt。若内容触发模型内容审核（如曾遇到的 Dashscope DataInspectionFailed），每次请求都会失败 —— 这也是为什么需要 /reset 同时清 session 与 MEMORY.md。

build_messages 细节

  • 运行时元数据（时间、channel、chat_id）打上 [Runtime Context — metadata only] 标记，与用户内容合并成同一条 user 消息，避免连续同角色被某些 provider 拒绝。
  • 多模态：图片用魔法字节检测 MIME，编码为 data:{mime};base64,... 的 image_url 块。

3.5 Provider 层 —— LLM 抽象与重试

nanobot/providers/base.py · registry.py

LLMProvider 抽象基类定义统一接口，并内置一套强大的重试与降级逻辑；registry.py 用一张 PROVIDERS 表驱动「模型名→provider」的自动匹配。

统一数据结构

@dataclass
class ToolCallRequest:    # 标准化工具调用
    id: str; name: str; arguments: dict
    def to_openai_tool_call(self) -> dict

@dataclass
class LLMResponse:
    content: str | None
    tool_calls: list[ToolCallRequest]
    finish_reason: str         # stop / tool_calls / error
    usage: dict                # prompt/completion/cached tokens
    reasoning_content: str | None   # DeepSeek-R1/Kimi 等
    thinking_blocks: list | None    # Anthropic 扩展思考

重试决策（_run_with_retry）

情况处理
非错误响应直接返回
非瞬时错误 + 含图片剥离图片重试一次（降级）
瞬时错误（429/500/timeout）standard重试 3 次，延迟 1/2/4 秒
瞬时错误 persistent无限重试，最大延迟 60s；相同错误 10 次后停止；等待期每 30s 心跳

新增 Provider 只要 2 步（注册表驱动）

这是 nanobot 最优雅的设计之一 —— 没有任何 if-elif 链。详见 开发指南 §4.2。支持的后端：openai_compat（默认）、anthropic、azure_openai、openai_codex、github_copilot。

3.6 工具体系

nanobot/agent/tools/

每个工具继承 Tool 抽象类，自描述 name/description/parameters(JSON Schema)，由 ToolRegistry 统一注册与执行。

class Tool(ABC):
    name / description / parameters     # 抽象属性
    read_only: bool = False             # 副作用自由→可并发
    exclusive: bool = False             # 必须独占运行
    concurrency_safe = read_only and not exclusive
    async def execute(**kwargs) -> Any  # 抽象方法
    cast_params() / validate_params() / to_schema()
工具类能力
filesystem.pyReadFile / WriteFile / EditFile / ListDir文件读写编辑、目录列举（支持图片、分页）
shell.pyExecTool执行 shell；内置危险命令正则黑名单（rm -rf / mkfs / dd / fork bomb 等）
web.pyWebSearchTool / WebFetchToolBrave/DuckDuckGo/Tavily/Jina/SearXNG 搜索 + 网页抓取
message.pyMessageTool主动发消息到指定渠道（含媒体）
cron.pyCronTooladd/list/remove 定时任务
spawn.pySpawnTool派生后台子代理
mcp.pyMCPToolWrapper把 MCP server 的工具包装成原生工具

文件工具通过 _resolve_path() 强制目录隔离；当 restrictToWorkspace=true 时所有路径必须落在 workspace 内，防止路径穿越。

3.7 渠道体系

nanobot/channels/

所有渠道继承 BaseChannel，实现 start/stop/send，可选实现 send_delta 支持流式。discover_all() 通过扫描包 + entry_points 自动发现内置与第三方插件渠道。

class BaseChannel(ABC):
    async def start() / stop() / send(msg)          # 抽象
    async def send_delta(chat_id, delta)            # 可选，流式
    def is_allowed(sender_id) -> bool               # allowFrom 鉴权
    async def _handle_message(...) -> None          # 收消息→鉴权→入总线
鉴权语义（安全默认）：
  • allowFrom = [] → 拒绝所有人（v0.1.4.post4 起）
  • allowFrom = ["*"] → 允许所有人
  • allowFrom = ["id1","id2"] → 白名单

ChannelManager 负责出站分发：合并连续的 _stream_delta 减少 API 调用、按 sendMaxRetries 做 1s/2s/4s 退避重试。

📌
线程级会话：Slack/Discord 在子线程里把 session_key 设为 slack:{chat_id}:{thread_ts}，每个线程独立会话。这也是之前删错 session 文件的根因。

3.8 会话管理

nanobot/session/manager.py

Session 持有完整消息列表 + last_consolidated 指针；SessionManager 提供内存缓存 + JSONL 持久化。

JSONL 格式

# 第一行元数据
{"_type":"metadata","key":"telegram:123","created_at":"...","last_consolidated":5}
# 后续每行一条消息
{"role":"user","content":"...","timestamp":"..."}
{"role":"assistant","content":"...","tool_calls":[...]}
{"role":"tool","tool_call_id":"...","name":"read_file","content":"..."}

「合法边界」对齐

get_history() 取 last_consolidated 之后的消息，并保证：① 从 user 回合开始；② 用 find_legal_message_start() 丢弃开头孤立的 tool 结果。这避免给 LLM 发送「有 tool 结果却没有对应 tool_call」的非法序列。

⚠️
缓存陷阱：SessionManager._cache 是进程级缓存。删磁盘 JSONL 文件对运行中的进程无效，必须重启或调用 invalidate()。/reset 命令正是通过 clear()+save()+invalidate() 一次性解决。

3.9 记忆系统

nanobot/agent/memory.py

双层记忆 + 基于 token 预算的自动压缩，是 nanobot 处理长对话的核心。

层文件作用
长期记忆MEMORY.mdLLM 提炼的事实，全量覆盖式更新，拼进 system prompt
历史日志HISTORY.md带时间戳的摘要段落，追加式，可 grep 检索

压缩触发逻辑（maybe_consolidate_by_tokens）

budget = context_window − max_completion_tokens − 1024(安全缓冲) target = budget / 2 若 估算 prompt token ≥ budget: 循环(最多5轮): pick_consolidation_boundary() # 选一个 user 回合边界 把该段旧消息发给 LLM → 调 save_memory 工具: history_entry → 追加 HISTORY.md memory_update → 覆盖 MEMORY.md session.last_consolidated = 边界 # 旧消息不再发给 LLM 直到 估算 ≤ target

失败兜底：连续失败 ≥3 次后 _raw_archive 把原始消息直接 dump 进 HISTORY.md，保证不丢数据。

3.10 配置系统

nanobot/config/

基于 Pydantic v2，支持 camelCase ⇄ snake_case 别名，配置文件 ~/.nanobot/config.json。

Config
├── agents.defaults    # model / provider / max_tokens / context_window_tokens
│                      # temperature / max_tool_iterations / timezone / ...
├── channels           # 各渠道配置 + 全局 sendProgress/sendMaxRetries
├── providers          # 20+ provider 的 apiKey/apiBase/extraHeaders
├── tools              # web / exec / restrictToWorkspace / mcpServers
├── api                # OpenAI 兼容服务器 host/port/timeout
└── gateway

Provider 自动匹配优先级（_match_provider）

1. provider != "auto" → 直接用指定的 2. 模型名显式前缀匹配 (anthropic/claude... → anthropic) 3. 关键词匹配 (按 PROVIDERS 注册表顺序) 4. 本地 provider 回退 (vLLM / Ollama，按 apiBase) 5. 任意已配 apiKey 的 provider（OAuth 除外）

关键默认值：model=anthropic/claude-opus-4-5、context_window_tokens=65536、max_tokens=8192、max_tool_iterations=200、temperature=0.1、timezone=UTC。

3.11 Cron / 总线 / 心跳 / API

⏰ Cron 服务 cron/service.py

三种调度：at（一次性时间戳）、every（周期 ms）、cron（表达式 + 时区）。持久化到 jobs.json，支持外部修改 mtime 自动重载，运行历史保留最近 20 条。

🚌 消息总线 bus/queue.py · events.py

两条 asyncio.Queue（inbound/outbound）。InboundMessage.session_key = session_key_override or f"{channel}:{chat_id}"。

💓 心跳服务 heartbeat/service.py

三阶段：① 决策（读 HEARTBEAT.md，LLM 用虚拟工具决定 skip/run）→ ② 执行（跑完整 agent 循环）→ ③ 评估（决定是否打扰用户）。用虚拟工具调用替代自由文本解析，更稳。

🔗 OpenAI 兼容 API api/server.py

POST /v1/chat/completions、GET /v1/models、GET /health。每用户会话锁串行，支持 session_id，暂不支持 stream=true。

4.4 新增一个工具

from nanobot.agent.tools.base import Tool

class WeatherTool(Tool):
    @property
    def name(self) -> str: return "get_weather"
    @property
    def description(self) -> str: return "查询某城市天气"
    @property
    def parameters(self) -> dict:
        return {
            "type": "object",
            "properties": {"city": {"type": "string", "description": "城市名"}},
            "required": ["city"],
        }
    @property
    def read_only(self) -> bool: return True   # 无副作用→可并发

    async def execute(self, city: str) -> str:
        ...  # 返回字符串结果
        return f"{city}: 晴, 22°C"

然后在 AgentLoop._register_default_tools()（或你的初始化处）self.tools.register(WeatherTool())。无副作用工具记得设 read_only=True 以享受并发。

4.5 新增一个技能（Skill）

技能是「教 LLM 如何做某类任务」的 Markdown 文件，渐进式加载（LLM 需要时才用 read_file 读全文）。

# workspace/skills/my-skill/SKILL.md
---
name: my-skill
description: "一句话描述这个技能做什么"
metadata: {"nanobot": {"always": false, "requires": {"bins": ["curl"], "env": []}}}
---

# 任务步骤
1. 第一步...
2. 第二步...

放在 workspace/skills/（用户级，优先）或 nanobot/skills/（内置）。always=true 的技能常驻 system prompt；requires 不满足的技能会被标记 available="false"。

易踩的坑（实战总结）

🐛
1. 删文件不生效 —— SessionManager 有进程级缓存，删 JSONL 必须重启或 invalidate()。
2. 删错 session 文件 —— 线程级会话 key 形如 slack:{chat_id}:{thread_ts}，文件名是 slack_C..._ts.jsonl，别只删 slack_C....jsonl。
3. MEMORY.md 污染 —— 长期记忆每次拼进 prompt，污染后需用 /reset 一并清除。
4. Telegram 命令被吞 —— 新命令要同步加进 telegram.py 的正则白名单。
5. allowFrom 空 = 拒绝所有 —— v0.1.4.post4 起的安全默认，想全开要写 ["*"]。
